# v1.0.1

A whole-band search in **0.14 seconds** instead of 12.5, and a band chart you can
actually use to scope one.

v1.0.0's headline interaction — click a channel on the band chart to tune it —
never worked, because of a Qt integer truncation described below. It also could
not scope a search to one band plan, which is both the workflow its own README
documented and the single biggest lever on how long a sweep takes. Both are
fixed here, along with a good deal more.

## Download

**`FPV-RF-v1.0.1-windows-x64.zip`**

1. Verify the download if you want to:
   ```
   sha256sum -c FPV-RF-v1.0.1-windows-x64.zip.sha256
   ```
   or in PowerShell:
   ```
   (Get-FileHash .\FPV-RF-v1.0.1-windows-x64.zip -Algorithm SHA256).Hash
   ```
2. Extract it. Everything lands in one `FPV-RF\` folder.
3. Double-click **`FPV-RF.exe`**.

Same procedure as v1.0.0. No Python, no pip, no drivers. Both radio helpers now
ship in the folder beside the app — `hackrf_transfer.exe` for samples, and
`hackrf_sweep.exe` for the fast search — and the app looks there before `PATH`.

## The headline: 0.14 s to search the whole US band

v1.0.0 walked the band one hop at a time, re-opening the USB device at each
stop. That re-open costs about 367 ms and it is all of the cost, so the 34 hops
across 5650–5950 MHz took 12.5 seconds and no amount of care in the app could
change that.

`hackrf_sweep`, from the same Mayhem bundle, keeps the radio open across a whole
sweep and retunes it with a control transfer. A hop then costs about a
millisecond:

| | v1.0.0 | v1.0.1 |
|---|---|---|
| Whole US band | 12.5 s, 34 hops | **0.14 s**, 320 bins |
| Can say a signal decodes as video | yes | no |

Only whole-band figures are quoted, because only they were measured. Scoping to
one plan narrows the span and the time with it; the numbers above are a
300 MHz sweep, so a 140 MHz plan is proportionally less.

**The engine is chosen for you.** The app uses the sweep when it can get the
radio and falls back to the hop walk when it cannot, and the status line says
which one answered. There is no new setting to understand.

The last row is the reason the hop walk still exists. A sweep measures energy
and never looks at a line rate, so it cannot tell you a signal is decodable
analogue video. When you want that, or when the sweep is unavailable, the hop
walk still runs and still tells you. Anything the app reports as decodable video
came from a real video field.

### Why it does not always win

Handing the radio over means stopping a transfer that is mid-stream, and on a
HackRF One that leaves the device refusing the next open for a period nobody can
predict — measured here from 0 s to over 30 s, and waiting does not reliably fix
it. When the sweep cannot get the radio the app falls back rather than sitting
there, so you always get an answer, and it says why in the status line.

If your scans are taking 12 s rather than 0.14 s, this is why, and it is a
property of the hardware rather than of the app.

## Passes

A new **passes** control sets how many sweeps to combine: 1, 4 or 10. One is the
default and it is right for FPV — the video link transmits continuously, so one
pass sees it as well as ten would, at 0.15 s against 0.53 s.

More passes only help against a transmitter that is *intermittent*. The combine
is a maximum rather than an average, deliberately: three consecutive single-pass
scans of the 2.4 GHz band showed spreads of 13, 42 and 15 dB, with one pass
catching a real WiFi signal at +42 dB that the other two missed entirely.
Averaging would have divided that signal by three and hidden it.

## Fixed

**Clicking a channel on the band chart never worked.** This is the one real bug
in v1.0.0. The chart declared `channelClicked = Signal(int)` and connected it to
a slot taking an int, which looks entirely reasonable — but Qt's int is a 32-bit
C int, and a frequency in Hz is about 5.8 × 10⁹. It was truncated on the way out
and the slot never resolved:

```
Overflow: Value 5865000000 exceeds limits of type [signed] "int"
AttributeError: Slot 'MainWindow::_on_channel_clicked(int)' not found
```

The signal was declared, connected, emitted and dropped, every time, silently,
for the life of v1.0.0. It is `Signal(object)` now, so the Python int arrives
intact. It was found by a test that drives the real widget and asserts on what
the slot received, not by reading the code — reading it, the signature is fine.

## Added

- **Band scoping.** Clicking a band row makes that plan the active one, which
  scopes both the search and auto-select to it. Clicking empty space below the
  rows clears it, so it is not a one-way door. Only clicks landing directly on a
  channel tick did anything at all in v1.0.0, and there was no active-band
  concept behind them, so the scan button always searched the whole US region.
- **An RF amplifier switch**, beside the LNA gain, and a real bypass rather than
  a gain change. The transfer helper takes `-a 0`, which leaves the LNA
  unpowered; asking for 0 dB of LNA gain instead leaves it powered and merely
  stops it amplifying. The app asks the binary which flags it understands before
  using `-a`, because that flag is a Mayhem extension and the stock Great Scott
  build treats an unknown option as a usage error — a change that would otherwise
  turn a working install into a dead radio. Leaving the checkbox out on a build
  that lacks the flag disables it and says why, rather than silently doing
  nothing.
- **A passes control**, described above.
- **`hackrf_sweep.exe` is bundled.** v1.0.0 shipped only the transfer helper, so
  the fast path was unavailable to anyone without a Mayhem folder already on
  their desktop. The fast engine itself is the headline of this release.

## One thing to know

`hackrf_sweep.exe` needs FFTW's single-precision library, `libfftw3f-3.dll`, which
the Mayhem bundle does not include. The app looks for a suitable build on your
machine — verifying it exports the right symbols, since a double-precision build
has the same file name and none of them — and stages a copy under
`%LOCALAPPDATA%\FPV-RF\`. It never writes to your Mayhem folder. FFTW is GPL and
this project is MIT, so it is staged at runtime rather than shipped.

If no suitable FFTW is found, the app says the fast path is unavailable and uses
the hop walk. That is a working app at 12.5 s, not a broken one.

## Checks

Everything above is measured rather than asserted.
`tools/check_sweep.py` runs the fast engine against hardware using the 2.4 GHz
band as a known answer, because it has traffic in it and 5.8 GHz does not, and
separately proves the empty 5.8 GHz band stays empty at 1, 5 and 20 passes.
`tools/check_fastscan.py` covers the engine choice and the radio handover.
`tools/probe_handover.py` reproduces the handover limitation described above.
The eight hardware-free checks run in CI on every push.

The live-radio check in `build_exe.py` warns rather than fails, so a build on a
machine with an unhappy radio still produces a verified build.
